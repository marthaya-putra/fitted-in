Progress stepper — redesign v2 (parallel-aware)

These designs model the real topology: summarize (gate) → summary · skills · experience (parallel) → format (join). Note: the parallel done events arrive in arbitrary order, so none of these assume a fixed finish sequence.

How to choose

1 · DAG — most literal topology. Great if you want users to see the parallelism. Busiest; needs the SVG care already shown.
2 · Parallel lanes — pipeline feel (think GitHub Actions). Each lane independent; arbitrary finish order looks natural. Balanced.
3 · Phase clusters — calmest & most scannable. Groups parallel work under one “Optimize” phase so it doesn’t read as 3 separate things. Quiet, professional.
4 · Parallel cards grid — most modern/app-like. Hero-izes the concurrent work; gate & join recede. Best if the 3 optimizations are the “interesting” part.
Implementation note: the extension already receives {stage, status} per branch with no timing data. Any of these can be driven purely from the existing events; per-branch durations (if wanted) must be derived client-side from the wall-clock gap between in-progress and done. The done events arrive in arbitrary order — all four designs above render correctly regardless of which branch finishes first.
